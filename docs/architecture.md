# BusAgent 架构说明

## 1. 目标

BusAgent 面向包含语言模型、感知算法和物理执行器的实时智能系统。其目标是在保持任务顺序、安全约束和可追踪性的前提下，让能够并行或流式执行的工作尽早开始。

架构优先级依次为：

1. **安全与可控**：模型决策不能越过硬件控制器、权限策略和人工确认边界；
2. **正确与可恢复**：消息可关联、任务可取消、失败可识别，重复投递不会造成重复物理动作；
3. **低交互延迟**：优先降低首次语音反馈、首次规划结果和首次感知请求的等待时间；
4. **可演进**：节点实现、模型供应商和底层传输可以替换；
5. **可观测**：一次用户意图的完整决策链可以检索、解释和回放。

## 2. 逻辑组件

### 2.1 消息总线

消息总线是投递与协调平面，而不是新的中央推理模型。它负责：

- 为入口指令生成全局唯一标识；
- 为派生消息维护因果关系、会话、任务和序号；
- 根据显式目标、主题或能力要求路由；
- 支持单播、多播、请求/响应、事件和流式分片；
- 应用超时、重试、背压、优先级和取消策略；
- 记录投递、确认、失败和监督结果。

总线不应自行解释业务意图，也不应隐式改写节点输出。需要语义判断时，应产生一条可审计的监督或路由决策。

### 2.2 能力注册表

注册表描述节点能做什么，而不是节点内部如何实现。每个节点注册：

- 稳定节点标识与版本；
- 输入、输出和流式能力；
- 可处理的消息类型；
- 并发模型和资源需求；
- 超时、幂等和重试特征；
- 权限、数据敏感级别和部署位置；
- 健康状态与负载信息。

路由可以直接指定节点，也可以声明能力要求后由总线选择满足条件的实例。

### 2.3 能力节点

节点可以由小模型、大模型、确定性算法、机器人服务、传感器、执行器或人工交互实现。节点只承担清晰职责，并对输入、输出、失败和下一跳建议负责。

节点可以建议下一跳，但建议不等于授权。总线需要结合能力注册、资源约束和监督策略决定是否投递。

### 2.4 任务与资源协调

计划描述任务之间的依赖关系和条件，不要求所有步骤线性执行。协调层维护：

- 等待、就绪、运行、暂停、完成、失败和取消状态；
- 任务依赖、分支条件和补偿操作；
- 机械臂、相机云台等独占资源的锁与队列；
- 高优先级安全事件的抢占；
- 同一物理动作的幂等键和执行凭证。

### 2.5 上下文仓库

上下文仓库保存可独立引用的分块，例如用户偏好、场景描述、任务计划、视觉结果和安全策略。消息只携带引用与版本，总线在投递前按节点权限和预算进行装配。

这种方式避免所有节点共享一个不断膨胀的全局上下文，同时允许复现某次决策实际看到的信息。

### 2.6 监督节点

监督节点对节点的路由建议、工具使用、上下文范围和安全策略进行检查。监督应以策略与证据为中心，避免演变成另一个包办所有任务的主 Agent。

对于物理执行，监督结果只是软件侧的一层防护，不能替代急停、力矩限制、碰撞检测和安全控制器。

### 2.7 可观测性

一次入口指令形成一条 trace，所有派生消息形成 span 或事件。最小观测集合包括：

- 消息创建、排队、投递、首个分片和完成时间；
- 节点输入引用、输出摘要、模型与提示词版本；
- 路由建议、监督判定和最终投递目标；
- 重试、超时、取消、丢弃和死信原因；
- 物理动作的审批、执行凭证与结果。

敏感原文与完整模型上下文必须根据数据级别进行脱敏、加密或禁止持久化。

## 3. 消息生命周期

一条消息通常经历以下阶段：

1. **接收**：入口适配器验证来源并创建消息信封；
2. **关联**：分配指令、会话、任务、因果和序列标识；
3. **装配**：解析上下文引用，并按权限与预算构建节点输入；
4. **监督**：对高风险或策略要求的路由进行允许、拒绝、替换或升级；
5. **排队**：依据目标节点、优先级、资源锁和背压规则等待；
6. **投递**：向节点发送完整消息或流式分片；
7. **确认**：节点确认接收、处理结果或失败；
8. **派生**：节点输出新消息，并继承必要的关联关系；
9. **归档**：写入最小审计记录，并按保留策略清理正文。

消息字段和状态定义见 [消息协议](message-protocol.md)。

## 4. 并发与顺序模型

### 4.1 可并行工作

不同节点、不同资源或无依赖的任务可以并行。例如，首次对话反馈不必等待完整计划，目标检测也可与计划解释同时进行。

### 4.2 有序工作

同一流的文本分片、同一任务的状态变更、同一机械臂的物理动作必须按定义的顺序处理。顺序范围必须显式声明，不能假设存在全局顺序。

推荐的顺序范围包括：

- `stream`：同一流内分片严格递增；
- `task`：同一任务的状态变更遵循状态机；
- `resource`：同一独占资源上的命令串行；
- `conversation`：需要连贯呈现的用户反馈按回复序列播放。

### 4.3 一次处理多个消息的节点

规划、聚合和监督节点可以并行处理多个任务，也可以在窗口内合并相关消息。合并必须保留原消息引用，并清晰说明输出基于哪些输入产生。

### 4.4 只能顺序处理的节点

机械臂执行器等节点通过资源队列串行消费。总线可并行准备后续动作，但只有获得资源租约且通过安全检查的动作才能进入硬件执行。

## 5. 交付与一致性

分布式系统中“绝对只投递一次”通常不可依赖。BusAgent 的目标语义是：

- 普通计算消息采用至少一次投递，并要求节点以消息 ID 去重；
- 流式分片可重放，接收方以流 ID 与分片序号去重和重排；
- 物理动作采用执行凭证、幂等键和状态查询，禁止因网络重试直接重复动作；
- 状态转换使用期望版本，防止过期结果覆盖新计划；
- 无法确定执行结果时进入人工或专用恢复流程，而不是盲目重试。

## 6. 背压、优先级与取消

节点必须暴露容量或由适配器维护队列上限。达到上限时，总线可延迟、降级、合并或拒绝消息。流式链路需要把下游压力向上游传播，避免无限缓存。

建议优先级从高到低为：

1. 急停、碰撞与人员安全事件；
2. 正在执行动作的取消或纠正；
3. 用户实时交互；
4. 任务规划与感知；
5. 后台总结、索引和分析。

取消是一等消息。取消入口指令后，所有未完成派生任务都应收到取消信号，但已经开始的物理动作需要由执行器决定安全停止点。

## 7. 故障处理

| 故障 | 默认处理思路 |
| --- | --- |
| 节点超时 | 标记超时；根据幂等性重试、切换实例或降级。 |
| 节点不可用 | 停止投递并根据能力注册选择替代节点。 |
| 流式分片缺失 | 在窗口内等待或请求重放；超时后终止该流。 |
| 过期结果 | 根据任务版本丢弃，不驱动新的物理动作。 |
| 低置信度感知 | 重新观察、切换感知策略或请求用户确认。 |
| 执行结果未知 | 查询硬件状态并进入恢复流程，禁止自动重复动作。 |
| 监督拒绝 | 记录理由，返回规划节点修正或升级给人工。 |

## 8. 传输与部署边界

BusAgent 定义的是上层消息和节点契约。实际传输可以由进程内通道、ROS 2/DDS、消息队列或其他技术实现。第一阶段应先定义传输无关语义，再通过适配器验证不同环境。

逻辑总线也不意味着必须部署为单一服务。控制面、消息代理、节点注册表和上下文仓库可以独立部署，但必须共享稳定的身份、协议版本和观测关系。

## 9. 安全边界

- LLM 不直接生成可绕过控制器的电机级命令；
- 所有物理动作必须经过确定性的边界、速度、碰撞与资源检查；
- 涉及人员附近动作、未知物体或低置信度目标时支持人工确认；
- 节点按照最小权限访问传感器、执行器和上下文；
- 外部输入与上下文内容均视为不可信，提示词不能替代访问控制；
- 审计记录需要能回答“谁在何时基于什么信息授权了什么动作”。

## 10. 待验证问题

- 节点自主选择下一跳与集中式路由策略应如何分工？
- 哪些消息需要强顺序，哪些只需要因果关系？
- 如何在流式输出尚未结束时撤回或纠正已合成语音？
- 监督节点如何避免成为新的延迟瓶颈和单点故障？
- 上下文分块如何进行版本化、过期和敏感级别传播？
- 面对真实机械臂，执行凭证与硬件状态如何形成可靠闭环？

这些问题应通过原型测量和 ADR 逐项收敛，不在文档阶段假设已有答案。
