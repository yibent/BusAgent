# 机械臂场景示例

本文用“找到绿色咖啡杯并递给我”说明目标架构如何并行工作。它是设计示例，不代表仓库中已有这些节点。

## 1. 场景前提

- 用户与机械臂位于同一受控空间；
- 系统具有语音输入、语音输出、视觉感知和机械臂执行能力；
- 执行控制器独立实施碰撞、速度和工作空间限制；
- 对话、规划和感知可以并行，单机械臂动作需要串行；
- 低置信度目标必须请求用户确认。

## 2. 事件时序

| 相对时间 | 事件 | 并行关系与目的 |
| --- | --- | --- |
| T0 | 语音转文字节点发布用户指令 | 创建 `instruction_id`，同时面向规划和对话能力。 |
| T0+ | 对话节点开始流式生成首次反馈 | 不等待完整计划，尽快让用户知道系统已开始处理。 |
| T0+ | 规划节点生成初始任务图 | 拆分为观察场景、定位目标、确认、规划抓取、执行和交付。 |
| T1 | 语音合成开始播放已提交的短句 | 与规划和视觉请求同时进行。 |
| T1 | 执行协调节点请求视觉感知 | 相机可用时立即开始，不占用机械臂动作资源。 |
| T2 | 视觉节点返回候选杯、位置和置信度 | 结果同时发给规划、对话和可选的指认节点。 |
| T3a | 置信度足够，规划节点提交抓取候选 | 进入确定性几何与安全验证。 |
| T3b | 置信度不足，指认节点请求用户确认 | 当前任务等待，机械臂不执行猜测动作。 |
| T4 | 执行协调节点取得机械臂资源租约 | 检查任务版本、执行凭证和控制器状态。 |
| T5 | 机械臂执行抓取与递送 | 每个动作阶段发布事实状态和异常事件。 |
| T6 | 对话节点根据事实结果生成完成反馈 | 只有执行器确认后才能宣告成功。 |

## 3. 初始计划示意

计划不是一段自然语言清单，而是带依赖与条件的任务图：

| 步骤 | 依赖 | 成功条件 | 失败或分支 |
| --- | --- | --- | --- |
| 获取场景 | 无 | 获得新鲜场景快照 | 重新采集或报告传感器不可用 |
| 定位绿色咖啡杯 | 获取场景 | 至少一个候选目标 | 调整视角或询问目标位置 |
| 消解目标歧义 | 定位目标 | 单一高置信度目标 | 请求用户指认 |
| 验证抓取 | 目标确定 | 轨迹、抓取点和安全约束通过 | 重新感知或拒绝执行 |
| 执行抓取 | 验证抓取 | 控制器确认持有目标 | 安全停止并进入恢复 |
| 递交用户 | 执行抓取 | 到达安全交付位并释放 | 请求用户配合或放置到安全位置 |

## 4. 同时到达第二条指令

假设机械臂正在抓取时，用户又说“把最左边的铅笔放进右边的箱子”。系统可以并行完成转写、规划和视觉准备，但不能直接与当前动作争用机械臂。

协调节点需要根据策略选择：

- 将新任务排队，保持当前安全动作完成；
- 如果用户明确要求取消，向当前任务发送取消消息，并由执行器选择安全停止点；
- 对高优先级安全事件立即抢占普通任务；
- 保持两条指令各自的任务版本和消息序列，避免视觉结果串线。

## 5. 低置信度与纠错

如果视觉节点发现两个绿色杯子，不能只把“最可能的那个”交给执行器。它应发布候选集合及置信度，规划节点转入确认分支，指认节点可通过语音、屏幕或机械臂安全指向询问“是靠近咖啡机的这个吗？”

用户回答后，新信息生成上下文分块并更新任务版本。此前基于旧目标生成的抓取结果即使稍后返回，也因版本过期而不得执行。

## 6. 失败示例

### 语音合成失败

规划和感知无需停止。对话消息可以转移到屏幕显示或稍后重试，但系统应避免用户在不知情时突然看到机械臂动作。

### 视觉节点超时

规划节点可以请求新的观察、切换感知节点或向用户说明暂时无法定位。执行节点不会收到未经验证的目标。

### 执行结果未知

网络中断后不能自动重发抓取命令。协调节点先查询控制器和传感器状态；无法确定时进入人工恢复流程。

### 用户中途取消

取消消息沿任务因果链传播。尚未开始的任务立即取消，流式语音停止在合适边界，机械臂由控制器执行安全停止或完成当前不可中断动作。

## 7. 建议测量

此场景的原型至少记录：

- 从语音转写完成到首个可播放语音分片的时间；
- 从指令到规划首个可执行步骤的时间；
- 从指令到视觉请求开始的时间；
- 完成任务的总时间；
- 用户纠正次数与错误目标率；
- 过期结果被正确丢弃的比例；
- 取消到各节点停止的时间；
- 并发两条指令时的资源与消息串线错误数。
