# 消息协议

本文定义 BusAgent 的概念消息模型。字段名与具体序列化格式尚未冻结，后续实现可以选择 JSON、Protobuf 或其他编码，但必须保留等价语义。

## 1. 消息信封

每条消息由稳定信封与业务内容组成。节点可以理解业务内容，但路由、追踪和可靠性不应依赖对正文做非结构化文本解析。

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `protocol_version` | 是 | 协议版本，用于兼容性判断。 |
| `message_id` | 是 | 每条消息的全局唯一标识，也是去重依据。 |
| `instruction_id` | 是 | 最初用户或系统指令的标识，贯穿完整处理过程。 |
| `correlation_id` | 是 | 一组请求、响应与派生事件的关联标识。 |
| `causation_id` | 否 | 直接导致本消息产生的上一条消息。 |
| `task_id` | 否 | 所属任务或计划步骤。 |
| `task_version` | 否 | 任务状态版本，用于识别过期结果。 |
| `source` | 是 | 发送节点或入口身份。 |
| `targets` | 是 | 一个或多个节点地址、主题或能力选择条件。 |
| `message_type` | 是 | 输入、命令、事件、结果、错误、取消、监督判定等类型。 |
| `delivery_mode` | 是 | 单条、流式、广播或请求/响应。 |
| `sequence_scope` | 否 | 顺序作用域，例如流、任务、资源或会话。 |
| `sequence_number` | 否 | 在顺序作用域内单调递增的编号。 |
| `context_refs` | 否 | 需要装配的上下文分块及版本引用。 |
| `priority` | 是 | 调度优先级；安全事件拥有独立最高等级。 |
| `created_at` | 是 | 带时区的创建时间。 |
| `deadline` | 否 | 超过该时间后结果不再有业务价值。 |
| `idempotency_key` | 否 | 副作用操作的幂等标识。 |
| `trace` | 是 | trace 与 span 关联信息。 |
| `content_type` | 是 | 正文的结构类型及其版本。 |
| `payload` | 是 | 业务内容或对外部内容的安全引用。 |

## 2. 身份与因果关系

不同标识解决不同问题：

- `instruction_id` 回答“这些工作来自哪一次原始指令”；
- `message_id` 回答“这是不是同一条投递或重放消息”；
- `correlation_id` 回答“哪些请求、分片和响应属于一次交互”；
- `causation_id` 回答“这条消息直接由谁产生”；
- `task_id` 与 `task_version` 回答“结果属于哪个计划步骤，是否已经过期”。

禁止只使用一个全局序号来表达所有顺序。不同会话和资源并行时，全局顺序会制造不必要的阻塞。

## 3. 地址与路由

目标可以用三种方式表达：

1. **节点地址**：明确投递给某个稳定节点或实例；
2. **主题**：投递给订阅某类事件的节点；
3. **能力选择**：声明所需能力、版本、地域、流式支持和权限，由总线选择实例。

节点输出可以携带“建议下一跳”和理由。总线在实际投递前仍需检查目标是否存在、协议是否兼容、节点是否有容量以及监督策略是否允许。

## 4. 流式消息

一个流至少包含以下事件：

| 事件 | 作用 |
| --- | --- |
| `stream.open` | 声明流 ID、内容类型、预计目标和初始元数据。 |
| `stream.chunk` | 携带分片序号、增量内容和可选校验信息。 |
| `stream.commit` | 表示此前内容可以被下游视为稳定输出。 |
| `stream.correct` | 在协议允许的窗口内修正尚未提交的内容。 |
| `stream.end` | 正常结束并给出最终分片序号。 |
| `stream.abort` | 终止流并给出原因、可重试性和最后有效序号。 |

流式消费者必须明确自己支持哪种语义：

- **增量消费**：收到分片即处理，例如文本转语音；
- **提交后消费**：只消费已经 commit 的片段；
- **完整消费**：缓存至 end 后一次处理。

当下游是语音合成时，已经播放的内容无法真正撤回，因此上游应以短句或语义稳定边界提交，避免把未经确认的长段推理直接说给用户。

## 5. 顺序、去重与重放

- 顺序只在 `sequence_scope` 内保证；
- 消费者以 `message_id` 去重，以作用域和 `sequence_number` 检测缺口；
- 流式分片允许在有限保留窗口内重放；
- 任务结果携带 `task_version`，旧版本结果可记录但不能推进新计划；
- 对物理动作，消息重放不等于动作重放，执行器必须检查执行凭证与当前硬件状态。

## 6. 确认与状态

建议区分以下确认层级：

| 状态 | 含义 |
| --- | --- |
| `accepted` | 总线接受消息并完成基本验证。 |
| `queued` | 消息已进入目标队列。 |
| `delivered` | 目标节点或适配器已收到消息。 |
| `processing` | 节点明确开始处理。 |
| `completed` | 节点成功产生约定结果。 |
| `failed` | 节点给出结构化失败。 |
| `cancelled` | 处理在安全边界内被取消。 |
| `expired` | 截止时间已过，结果不再被采用。 |

“消息已送达”和“物理动作已完成”必须是不同状态，不能用代理确认冒充硬件事实。

## 7. 错误模型

错误至少应包含：

- 稳定错误代码与人类可读摘要；
- 发生错误的节点、阶段和关联消息；
- 是否可重试，以及建议的最早重试时间；
- 已产生的副作用和其确定性；
- 可用的降级或人工处理建议；
- 经脱敏的诊断引用。

错误正文不得泄露凭据、完整提示词、私有上下文或不必要的传感器数据。

## 8. 兼容性

- 协议版本使用明确的主版本兼容规则；
- 新增可选字段时，旧节点应能安全忽略；
- 删除字段或改变语义需要提升主版本；
- 节点注册时声明支持的版本范围；
- 总线不应在没有可审计转换记录的情况下静默转换有副作用的命令。
