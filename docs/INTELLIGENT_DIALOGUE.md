# 即时对话与可检索上下文（2026-09-07）

完整的 `intent.created` 同时送到回答节点和智能规划节点。ASR 片段只更新转写和执行轻量打断检测，不调用回答模型，也不为每个片段创建执行时间线节点。

- 回答节点根据用户原话、当前工作和对话上下文生成一句即时回应。
- 规划节点查询历史/场景或生成计划，通过 `intelligence.reply` 返回有来源的结果。
- 回答节点结合原问题组织最终答复。`instruction_id` 关联整个回合；结果先到时取消尚未发出的接话。新用户发言可以打断旧回应。同一回合相同答复去重。
- 新请求的规划最多并行两项，与动作执行/监督分开调度。信息查询返回 `chat`，无动作步骤；准备好的动作按机械臂队列执行，必须等待当前动作真实终态。
- 明确停止的轻量检测保持独立，不等待 LLM。ASR 重传按服务事件 ID、音频 item、utterance ID 和序号去重，不按文字内容去重，因此用户再次说相同的话仍然有效。

## 上下文

`ContextMemory` 从 MySQL 中的原始 Bus 事件和持久化任务队列构建视图，不依赖进程内聊天数组。

1. **当前工作**：原始要求、完成条件、任务修订号、剩余步骤、持物状态、最新执行证据。优先放入正在执行/规划的任务，旧 blocked 任务排在后面。
2. **近期原文**：最近十条相关记录保留原文，按完整记录选择，避免截断否定句。
3. **历史事件摘要**：同一请求的重复进度合并成事件摘要，保留用户要求、最后的规划报告/助手说法及独立的执行证据。任务摘要由真实步骤状态构建，不通过另一次 LLM 调用推测成功。
4. **可回查档案**：所有原始事件仍在 MySQL。规划模型可通过 `read_history` 按原事件引用、任务引用、关键词和分页游标读取；对话内容限定当前会话，共享机械臂任务历史来自队列。

视图使用保守的中英文 token 估算，回答接话/结果默认预算分别为 2400/4200，规划会话记忆为 4500。超出预算只省略完整记录，并提供省略数量、可检索提示及来源引用。当前规划目标和本轮用户原话还会单独提供。该预算限定共享会话记忆，不代表整个视觉规划请求的总 token 上限。

助手说过“成功”只是历史话语，不能替代执行证据。已有的视觉规划证据压缩继续使用 `planning-context.ts`；不把图像、点云、掩码复制进对话记忆。当前页面会话 ID 在同一浏览器标签刷新后延续，显式“新会话”才更换。

## 成本与配置

前端模型设置新增“即时回答模型”，未单独配置时使用规划模型的 profile。回答与规划共享同一份模型配置实例，保存设置后立即生效。接话最多 48 个输出 token，结果最多 600；接话/结果模型阶段总超时分别 3.5/6.5 秒，至多尝试两个已配置 profile。不可用时接话用最小收件提示，结果回退为规划节点原始事实文本。

不会每轮额外调用模型生成记忆摘要。正常的短操作不因这个修改增加机械执行监督次数；信息查询不再等待机械执行队列。

## 验证

- 本地覆盖语音重传、真实停止保留、并行历史查询、回应竞态、模型故障回退、任务顺序、历史检索、否定/失败证据保留和独立模型设置。
- 云端 Qwen + BusAgent WebSocket：询问“我们刚才都干了啥”及后续“哪一步成功了”，能够结合实际任务记录回答；两条查询都是零动作。
- 云端 Qwen TTS 合成问句 → 实时 ASR → Bus → 回答/规划 → TTS：1 条最终转写、1 条 intent、0 个流式重复节点、0 个动作；转写后约 0.82 秒接话。这是合成语音接口测试，不等同于真实麦克风的噪声/回声测试。
- 后端重启后沿用同一会话追问，仍能查到原对话并正确回答；前端已验证“即时回答模型”选择入口。
- 一次历史查询首答约 1.1 秒，完整结果约 7–15 秒，主要耗时仍在规划模型的查询和推理；这不是吞吐基准或延迟保证。
