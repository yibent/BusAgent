最重要的一条原则是：

节点名称必须描述“职责”，不能描述“用了什么模型”。

因此不应该有一个笼统的 LLMNode 或 VLANode。应该有：

InstructionUnderstandingNode，其实现可以是 Qwen、规则模型或其他 LLM；
RecoveryPlannerNode，其实现可以是 LLM、行为树或规则系统；
FineManipulationPolicyNode，其实现可以是视觉伺服、导纳控制、ACT、Diffusion Policy 或 VLA；
PlacementVerifierNode，其实现可以是几何规则、VLM 或两者集成。

这正符合文档中“每个节点声明唯一职责、输入输出、并发模式、流式能力、下一跳白名单、超时、重试与资源车道”的节点契约思想。

一、首先划清：哪些东西绝不能做成普通插件

BusAgent 中有一部分应该是框架内核，而不是任意模型可以替换的业务节点。

1. 消息与因果内核

以下语义必须固定：

message_id
bus_seq
instruction_id
causation_id
task_id
task_version
sequence_scope
lane_key
priority
deadline
context_refs
流式分片顺序
幂等去重
取消传播

具体用 NATS、DDS、ROS 2、Redis Streams 或进程内队列可以替换，但上面的语义不能被插件重新定义。

2. 资源车道和版本控制

以下机制也必须在内核里：

机械臂车道严格串行；
旧 task_version 结果自动丢弃；
任务取消沿因果链传播；
结果为 unknown 时禁止盲目重发；
节点超时不能自动解释成“执行失败”；
每次物理执行都必须有凭证。

这些是 BusAgent 成立的基础，不应由 LLM、VLA 或某个业务节点决定。

3. 最终执行闸门

模型和规划器只能产出：

ActionProposal
TrajectoryProposal
SkillProposal

最终是否允许进入机器人控制器，必须经过一个固定的 ExecutionGate。

即使替换了监督模型、规划器或 VLA，也不能绕过这个闸门。

4. 物理安全控制

急停、碰撞停止、关节限位、速度限制、力矩限制以及高频控制回路，不属于普通 BusAgent 插件。报告本身也明确把 BusAgent 定位在语义决策层，底层功能安全由机器人控制器独立承担。

因此：

应急检测器        可以插拔
碰撞感知算法      可以插拔
安全状态上报适配器 可以插拔

但：

急停执行
力矩限制
安全速度监控
控制器保护

不能依赖 BusAgent 中某个可能超时或崩溃的节点。

二、我建议的完整可插拔节点目录

下面是我认为 BusAgent 应该正式定义的逻辑节点族。

这里的“节点族”不代表一定要启动同样数量的进程。例如快速检测和场景图融合可以部署在同一进程，但逻辑契约仍然应分开。

A. 交互与语义节点
1. InputAdapterNode

负责把不同入口统一为 InputEvent：

麦克风；
文本输入；
触摸屏；
PLC；
MES 指令；
远程 API；
物理按钮。

输出至少包含：

source
timestamp
user/session
priority
payload

这样 BusAgent 不会与“语音输入”绑死。

2. ASRNode
AudioChunk
    ↓
TranscriptChunk

可替换实现：

FunASR；
SenseVoice；
Whisper 类模型；
云端 ASR；
工业关键词识别器。

它应当与指令理解分开，因为 ASR 是流式、高频输入，而指令理解是语义处理。

3. InterruptMonitorNode——建议新增

这是我认为当前文档里非常需要补上的节点。

它只负责识别：

“停”；
“等一下”；
“取消”；
“先别动”；
控制台暂停按钮；
PLC 中止信号；
高优先级抢占请求。

它不负责完整理解用户意图，而是先输出：

{
  "event": "interrupt_requested",
  "source": "voice",
  "confidence": 0.96,
  "scope": "arm-01"
}

BusAgent 收到后先触发确定性的 HOLD，再由普通语言模型慢慢判断用户究竟是：

暂停；
取消；
修改目标；
调整优先级。

这样“立即停下来”不依赖完整 ASR、LLM 或 VLA。

4. InstructionUnderstandingNode
Transcript
    ↓
IntentFrame

输出结构化字段：

intent；
target category；
attributes；
spatial reference；
destination；
quantity；
constraints；
是否需要澄清。

这就是文档已有的 Qwen3 加受限解码节点。

5. GroundingClarificationNode
IntentFrame + SceneSnapshot
              ↓
GroundedCommand
       或
ClarificationRequest

它解决的是：

“左边的扳手”到底是哪一个；
“最近的滚柱”是哪一个；
“第三格”对应什么坐标；
多个候选是否足够接近，需要询问用户。

它不能只靠语言模型，必须消费当前场景图。

6. DialogueNode

输入不是原始相机画面，而应该是：

任务状态；
环切换事件；
感知结果摘要；
执行状态；
失败与恢复事件。

输出流式文本：

“收到，我去找滚柱。”
“靠近了，我慢一点对准。”
“前面的路径被挡住了，我正在重新规划。”
7. OutputAdapterNode

统一输出到：

TTS；
屏幕字幕；
HMI；
PLC 状态位；
API 回调；
告警灯。

TTS 可以是其中一个独立实现，但不应该让整个系统只支持语音。

文档当前的交互链、规划链和执行链本来就是并行的，这些交互节点应继续保持独立，不能重新合并为一个主模型。

三、任务规划与治理节点
8. TaskPlannerNode

输入：

GroundedCommand
SceneSnapshot
TaskState
AvailableSkills

输出：

TaskPlan / Task DAG

它只生成技能级计划，例如：

perceive
select_target
plan_grasp
move_to
grasp
transport
place
verify

不能输出电机命令或自由文本动作。

9. PlanValidatorNode

文档中的“符号校验器”应该正式独立成一个节点，而不是隐藏在 Task Planner 内部。

它检查：

参数类型；
前置条件；
后置条件；
工作空间；
目标格占用；
技能顺序；
是否存在不可达或循环步骤；
当前任务版本是否仍有效。

任务规划器可以替换，但验证器必须始终存在。文档已经规定语言模型只从技能库选技能，并由确定性校验器保证任务序列合理。

10. ExecutionCoordinatorNode

它负责：

推进任务状态机；
发起技能调用；
等待技能结果；
更新当前步骤；
请求新的感知；
触发验证；
请求恢复；
请求内核生成新任务版本。

它不能直接控制机器人，也不能自己绕过验证器。

我建议将目前“执行协调”节点中的部分路由决策拆出去。

11. LoopRouterNode——建议从执行协调中拆出

它负责选择：

这一阶段使用哪条控制环
以及使用哪一种节点实现

例如：

fine_grasp_geometry
fine_grasp_visual_servo
fine_grasp_act
fine_grasp_vla

输入：

当前任务阶段；
零件类别；
当前置信度；
精度要求；
延迟预算；
历史成功率；
当前节点健康状态；
可用算力。

输出：

{
  "loop_profile": "fine_grasp_visual_servo",
  "fallbacks": [
    "fine_grasp_act",
    "fine_grasp_vla"
  ]
}

报告已经提出同一阶段允许有多个候选环，同一个节点也可以出现在多个环里。

因此“环”应当是一个可加载的图配置，而不是写死在执行协调节点内部。

12. SemanticSupervisorNode

监督节点本身可以插拔：

规则监督器；
小 LLM；
风险分类模型；
多模型投票；
工业规则引擎。

但它只是给出：

approve
reject
require_human
tighten_constraints

真正阻止动作的执行闸门仍然是固定内核。

监督节点应保持旁路，不能变成所有消息都必须经过的中央主模型。

13. RecoveryPlannerNode

输入：

FailureContext
CurrentTaskState
SceneSnapshot
AvailableRecoverySkills

输出：

RecoveryPlan

例如：

change_grasp_angle
reobserve
retreat_and_reapproach
safe_place
wait_clearance
move_blocker
request_human

这里非常适合使用 LLM，但不需要 VLA。

它不直接把 task_version 加一，而是提交恢复方案；由执行协调和内核创建新的任务版本。

四、感知与世界建模节点

当前文档里的“视觉感知”节点太宽。我建议至少拆成下面几类。

报告已经明确区分了快速接近、精细抓取和放置校验三个不同周期的环：快速检测与路径规划用于接近，精确分割、6D 位姿和力反馈用于精细阶段，几何与 VLM 用于校验。

14. FastPerceptionNode

面向快环，负责：

目标检测；
粗实例分割；
跟踪；
粗略三维位置；
遮挡分数；
置信度。

候选实现：

YOLO；
RT-DETR；
RTMDet；
轻量视觉提示检测器。

输出统一为：

ObjectObservation[]

不允许每个模型输出自己独有的数据格式。

15. PrecisePerceptionNode

面向最后几厘米，负责：

ROI 精确分割；
局部关键点；
6D 位姿；
零件轴向；
接触区域；
放置格口边缘。

候选实现：

SAM2；
CAD 配准；
关键点网络；
位姿估计网络；
几何视觉。
16. OpenWorldRecognitionNode

这是慢环和共享服务器上的可选节点。

负责：

未知对象识别；
文本提示检测；
视觉提示匹配；
新类别原型生成；
新物体登记。

它可以使用 VLM、开放词汇检测器，但不应放在正常快环关键路径。

17. SceneGraphFusionNode——建议显式新增

文档中已经多次使用“场景快照”和“场景图”，但我建议把它正式独立成节点。

它负责融合：

多相机观测；
同一物体跨帧身份；
世界坐标；
物体姿态和不确定度；
料箱格占用；
动态障碍物；
观测时间；
信息是否过期。

输出示例：

{
  "scene_version": 82,
  "timestamp": 123.45,
  "objects": [...],
  "bin_occupancy": {...},
  "dynamic_obstacles": [...],
  "frame": "robot_base"
}

LLM、任务规划器和恢复节点都不应该自己解析原始检测框，而应该消费这个场景图。

18. DynamicSceneMonitorNode——建议新增，且必须部署在本地

这是处理“路径突然被挡住”的核心节点。

它持续监控：

障碍物进入路径；
人手进入工作区；
目标物被移动；
原有轨迹对应的场景版本已经过期；
运输中的零件掉落；
相机检测到明显场景变化。

输出：

PathInvalidated
TargetMoved
HumanIntrusion
SceneChanged

它不负责重新规划，也不负责理解“该怎么办”。

它只负责快速、确定地宣布：

当前轨迹不再可信。

19. ManipulationGoalPlannerNode

我建议把当前“抓取规划”中的目标生成和路径规划拆开。

这个节点负责生成：

抓取候选；
预抓取位姿；
夹爪方向；
夹爪宽度；
接近方向；
放置位姿；
安全临时放置区域；
允许的接触方向。

候选实现：

mask 质心 + PCA；
CAD 抓取模板；
抓取网络；
关键点规则；
learned affordance model。

输出的是：

GraspCandidate[]
PlacementCandidate[]

而不是完整轨迹。

五、运动、接触与硬件节点
20. MotionPlannerNode

负责自由空间运动：

start state
goal pose
scene graph
constraints
    ↓
trajectory / no_path

可替换实现：

cuRobo；
MoveIt；
OMPL；
MPC；
厂商规划器。

它应该返回明确的失败原因：

NO_IK
NO_PATH
COLLISION
GOAL_OUTSIDE_WORKSPACE
SCENE_STALE
TIMEOUT

不能只返回一个模糊的 failed。

21. TrajectoryValidatorNode

这是轨迹级的确定性验证节点，与任务级的 PlanValidatorNode 不同。

检查：

轨迹使用的场景版本是否仍有效；
最小碰撞距离；
速度、加速度和加加速度；
夹持状态下的姿态约束；
是否穿过禁区；
是否符合当前工具或零件限制。

它输出“可执行轨迹候选”，之后仍需固定执行闸门签发凭证。

22. FineManipulationPolicyNode

这就是 VLA 最适合插入的位置。

统一输入：

目标局部状态
腕部 RGB-D
机器人当前状态
夹爪状态
力/力矩状态
允许动作范围
任务版本
观测时间

统一输出：

BoundedActionProposal

它可以有多种实现：

visual_servo_policy
admittance_force_policy
act_policy
diffusion_policy
vla_policy
teleoperation_policy

VLA 不应直接成为 BusAgent 的特殊成员，它只是这个接口的一种 provider。

例如：

FineManipulationPolicyNode
├── geometry_visual_servo
├── visual_servo_admittance
├── ACT
└── VLA

所有实现必须输出：

action 或 action chunk；
置信度；
有效截止时间；
使用的 observation ID；
task_version；
可中断点；
建议停止条件。

模型输出过期、任务版本变化、场景变化时，整个 action chunk 直接作废。

23. DeviceAdapterNode 节点族

至少包括：

CameraAdapterNode
RobotAdapterNode
GripperAdapterNode
ForceTorqueAdapterNode
TransformProviderNode

文档已经定义了 Robot、Gripper、Camera 三层接口，并要求仿真与真机共享相同方法签名；这本身就是非常适合插件化的边界。

其中：

RobotAdapter

只能接受带执行凭证、版本有效的命令，并返回：

accepted
started
completed
failed
unknown

不能让不同品牌的机器人各自重新定义状态语义。

六、验证、恢复和学习节点
24. GraspVerifierNode

应该从“抓取规划”或“机器人执行”中独立出来。

输入：

夹爪开度；
夹持力；
腕部相机；
末端状态；
搬运初期的稳定性。

输出：

grasped
empty
slipping
uncertain

这使不同夹爪、视觉验证器和力传感器可以单独替换。

25. PlacementVerifierNode

文档中已有这一节点。

输入：

放置前后的场景；
目标格；
零件 ID；
几何状态；
可选 VLM 判断。

输出标准化为：

seated
tilted
wrong_cell
missing
occupied
uncertain

几何规则、VLM 或融合方案只是不同 provider。

26. MemoryUpdaterNode——建议正式独立

文档已经定义了三种可分别共享的长期记忆：

视觉记忆；
机械记忆；
用户记忆。

我建议让专门节点负责写入，而不是由感知、规划或恢复节点直接修改数据库。

它消费：

Observation
ExecutionResult
VerificationResult
FailureRecord
UserCorrection

然后产生版本化更新：

VisualPrototypeUpdate
GraspStatisticsUpdate
RouteSuccessUpdate
UserPreferenceUpdate

尤其要注意：

在线学习节点不能在关键路径上悄悄替换生产模型。

新原型、新权重和新策略应先生成候选版本，通过仿真或回放评估，再由显式的模型晋级机制启用。

27. HealthFallbackNode——建议新增

它监控的不是任务本身，而是节点健康：

推理延迟突然升高；
VLA 超时；
相机帧过期；
深度连续缺失；
标定漂移；
GPU 不可用；
模型持续低置信；
共享服务器断开；
节点输出 schema 异常。

它可以触发：

切备用检测器
切确定性策略
降速
只使用主相机
进入 HOLD
转人工确认

这个节点对“可插拔架构”特别重要。因为插件越多，就越必须定义：

插件失效时系统如何退化，而不是整个 BusAgent 一起失效。

28. SimulationFaultInjectionNode 与 ReplayEvaluatorNode

这些不需要在生产关键路径常驻，但应使用与真机节点相同的接口：

Isaac Sim 设备适配器；
虚拟相机；
虚拟机械臂；
故障注入；
消息回放；
新插件离线评估；
A/B 测试；
延迟与成功率统计。

这样替换一个模型后，可以把真实任务日志重新回放，判断新插件是否会改变决策。

七、不仅节点要可插拔，控制环也要可插拔

节点解决“谁提供能力”，控制环解决“当前阶段组合哪些能力”。

我建议至少定义这些环模板：

interaction_loop

approach_fast_loop

fine_grasp_geometry_loop
fine_grasp_learned_loop
fine_grasp_vla_loop

transport_loop

fine_place_loop

verification_loop

obstacle_replan_loop

interrupt_safe_transition_loop

recovery_loop

例如：

fine_grasp_geometry_loop
=
PrecisePerception
→ ManipulationGoalPlanner
→ VisualServoPolicy
→ RobotAdapter
→ GraspVerifier

而：

fine_grasp_vla_loop
=
PrecisePerception
→ VLAProvider
→ TrajectoryValidator
→ RobotAdapter
→ GraspVerifier

二者对上层暴露相同结果：

grasped / empty / failed / uncertain

所以执行协调器不需要知道下面究竟用了视觉伺服还是 VLA。

报告本身已经提出：模型更换只应影响环组成、选择逻辑和节点内部实现，框架本身保持不变。

八、技能也应该是插件，但技能不是普通节点

文档已有：

perceive
select_target
plan_grasp
move_to
grasp
transport
place
verify_placement
recover

我建议再增加：

hold
resume
cancel
retreat
reapproach
safe_place
wait_clearance
replan
change_grasp
change_approach
move_blocker
handover
request_human

一个技能插件应该声明：

名称
参数 schema
前置条件
后置条件
占用车道
可中断性
安全停止点
失败类型
最大重试次数
对应环模板

例如：

skill: safe_place
preconditions:
  - gripper.holding_object == true
parameters:
  - safe_region
postconditions:
  - gripper.holding_object == false
lane:
  - arm-01
interruptibility: at_servo_boundary
loop_profile: fine_place_loop

这样 LLM 选择的是 safe_place，不是自由生成“往右移动 20 厘米再松手”。

九、用几个场景检验这套插件划分
场景 1：正常抓取滚柱
InstructionUnderstanding
→ Grounding
→ TaskPlanner
→ PlanValidator
→ FastPerception
→ SceneGraph
→ ManipulationGoalPlanner
→ MotionPlanner
→ RobotAdapter
→ FineManipulationPolicy = visual servo
→ GraspVerifier
→ PlacementVerifier

这里完全不需要 VLA。

场景 2：运输途中路径突然被挡住
DynamicSceneMonitor
→ PathInvalidated
→ 固定执行闸门停止旧轨迹
→ MotionPlanner 重新规划

若重新规划成功：

直接继续

若返回 NO_PATH：

RecoveryPlanner
→ wait_clearance / safe_place / move_blocker / request_human
→ PlanValidator
→ 新任务版本

VLA只有在“移动障碍物本身属于复杂接触操作”时，才可能作为 FineManipulationPolicy 的实现被调用。

场景 3：用户中途说“等一下，先拿扳手”
InterruptMonitor
→ 立即 HOLD
→ 旧任务停止继续派发

与此同时：

ASR
→ InstructionUnderstanding
→ priority_change
→ RecoveryPlanner

若手中有零件：

safe_place
→ 让出 arm-01
→ 扳手任务开始

这与文档已有的“持物时先安全放置、再切换任务”逻辑一致。

关键是：即时 HOLD 不等待完整 LLM 推理。

场景 4：第一次出现未知零件
FastPerception 低置信
→ LoopRouter
→ OpenWorldRecognition
→ PrecisePerception
→ SceneGraph
→ MemoryUpdater

同批次后续对象可以优先复用视觉原型。

场景 5：几何抓取连续失败

第一次：

FineManipulationPolicy = visual servo
→ GraspVerifier = empty

第二次：

RecoveryPlanner = change_grasp
→ geometry policy

继续失败：

LoopRouter
→ FineManipulationPolicy = ACT / VLA

这才是合理的模型升级路径。

场景 6：VLA 太慢或共享服务器不可用
HealthFallbackNode
→ VLA timeout
→ 当前结果标记过期
→ 切 visual_servo_admittance

若确定性策略不满足精度：

安全 HOLD
→ 请求人工确认

不能因为 VLA 挂了，机械臂就处于一个没有明确控制权的中间状态。

所以我的完整结论是：

BusAgent 的真正可插拔对象不是“模型”，而是能力节点、控制环和技能。

LLM 应作为指令理解、任务规划、对话和恢复规划节点的可替换实现；VLA 应只作为 FineManipulationPolicyNode 的一种可替换实现；感知模型、运动规划器、验证器和硬件适配器也都必须处在各自独立的插件槽中。

版本、车道、执行凭证、取消、审计和底层安全则必须固定在框架内核中，任何插件都不能重新定义或绕过。

这会使 BusAgent 真正做到：换模型不换框架，换机器人不换上层，换任务只增加技能和环配置，而不是重新搭建整套系统。
