# 上下文仓库

## 1. 目的

BusAgent 不让每个节点自动继承完整会话与全局状态。上下文仓库将信息拆成可引用、可版本化和可授权的分块，消息通过 `context_refs` 指明需要哪些内容，总线在投递前完成装配。

这种设计希望同时降低上下文成本、减少无关信息干扰，并保留决策复现能力。

## 2. 上下文分块

一个上下文分块至少包含：

- 全局唯一的分块 ID；
- 类型与结构版本；
- 内容或安全的外部对象引用；
- 创建者、创建时间和来源消息；
- 当前版本与父版本；
- 所属用户、会话、任务或环境范围；
- 敏感级别与访问策略；
- 过期时间和保留策略；
- 完整性校验信息；
- 可选的摘要、标签和检索索引。

典型分块包括用户偏好、当前任务计划、场景快照、目标候选、对话摘要、设备状态和安全策略。

## 3. 引用与装配

引用应尽量固定到明确版本。允许请求“最新版本”时，装配结果必须记录最终解析到的版本，确保事后可以复现。

装配过程遵循：

1. 验证消息和目标节点身份；
2. 解析引用与版本；
3. 检查节点权限、用途和数据地域；
4. 应用大小或 token 预算；
5. 必要时使用经过记录的摘要或裁剪策略；
6. 生成本次请求的上下文清单与校验值；
7. 将装配结果交给节点，并记录实际使用版本。

节点不能把“看不到某块上下文”当作读取失败后自动扩大权限的理由。

## 4. 版本与并发更新

上下文更新采用追加新版本的方式，避免覆盖历史事实。写入者携带预期父版本；若当前版本已经变化，应进行显式合并或重新规划。

任务计划、设备状态等动态上下文需要区分：

- **事实**：传感器或执行器报告的已发生状态；
- **推断**：模型或算法根据事实得到的判断；
- **意图**：计划执行但尚未发生的动作；
- **策略**：限制哪些动作可以被提出或执行。

四类信息不可混写，否则节点可能把计划误当成已经执行的事实。

## 5. 生命周期与隐私

- 瞬时流式分片在完成后可以只保留摘要和校验信息；
- 原始音频、图像和完整提示词使用更短保留期；
- 用户偏好需要明确来源和撤销机制；
- 安全审计记录可有更长保留期，但必须最小化敏感正文；
- 删除请求需要传播到副本、索引和派生摘要；
- 训练或评估用途必须与运行用途分开授权。

## 6. 检索边界

语义检索可以帮助选择上下文，但检索结果仍必须经过权限、版本和任务相关性过滤。外部内容和历史对话都可能包含提示注入，不应因进入上下文仓库就被视为可信指令。

## 7. 衡量指标

- 单节点平均装配上下文大小；
- 无关上下文比例与裁剪命中率；
- 因版本冲突导致的重规划次数；
- 权限拒绝和敏感信息泄露事件；
- 决策回放时上下文完整还原率；
- 摘要前后关键事实保持率。
